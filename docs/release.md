# Zorg MVP Release Process

This document defines the non-publishing release process for the Zorg v1 MVP
across the Rust, Tree-sitter, and Neovim repositories. It is the operator
checklist for a later tagged release and the contract for local dry runs.

The MVP release uses sibling checkouts by default:

- `../zorg`: Rust workspace, `zorg` CLI, `zorg-ls`, shared docs, and canonical
  fixtures.
- `../zorg-treesitter`: Tree-sitter grammar, query files, corpus tests, and
  generated parser boundary.
- `../zorg-nvim`: Neovim plugin, command wrappers, LSP setup, health checks,
  help docs, and runtime query files.

Override sibling paths with `ZORG_TREESITTER_DIR` and `ZORG_NVIM_DIR` when the
repos are not adjacent.

## Release Train and Versions

The first MVP release uses a coordinated release train. The Rust workspace,
Tree-sitter package metadata, and Neovim plugin docs should all describe the
same public release version even though the repositories can be tagged
independently.

Current planned MVP version:

- Rust workspace: `Cargo.toml` `[workspace.package].version = "0.1.0"`.
- Rust binaries: `zorg --version` and `zorg-ls --version` report the workspace
  package version.
- Tree-sitter metadata: `../zorg-treesitter/package.json` `version = "0.1.0"`.
- Neovim plugin: no package manifest owns a version. The release tag and
  release notes carry the coordinated version.

Before `1.0.0`, breaking changes are signaled by increasing the minor version.
Patch releases should be limited to compatible fixes, documentation corrections,
and packaging repairs. If only one repository changes for a patch release, the
release notes must still name the unchanged sibling versions that were validated
together.

## Changelog Policy

Each repository should use `CHANGELOG.md` once the first real release is cut.
Until then, release notes may be staged in this file or the release operator's
draft, but the final tagged release must add or update `CHANGELOG.md` in every
repo that is part of the release train.

Required sections for each release entry:

- `Added`
- `Changed`
- `Fixed`
- `Validation`
- `Packaging`

Cross-repo changes must reference the sibling repository and commit or tag when
the behavior depends on another repo. Example: a Neovim query update should
reference the `zorg-treesitter` query commit it mirrors, and a Rust parser
release should reference the generated grammar commit it consumes.

The `Validation` section must name the exact `tools/validate_cross_repo.sh`
result used as the pre-release gate.

## Binaries and Archives

The Rust release ships two command names:

- `zorg`
- `zorg-ls`

Initial binary targets:

- `x86_64-unknown-linux-gnu`
- `aarch64-unknown-linux-gnu`
- `x86_64-apple-darwin`
- `aarch64-apple-darwin`
- `x86_64-pc-windows-msvc`

Archive naming:

- Unix: `zorg-v{version}-{target}.tar.gz`
- Windows: `zorg-v{version}-{target}.zip`

Each archive must contain `zorg`, `zorg-ls`, license files, README, and release
notes. Checksums are required for every archive:

- `{archive}.sha256`

Cryptographic signing is deferred for the MVP. If signatures are added later,
they must be detached signatures named `{archive}.sig` and the public key or
verification command must be documented before publishing.

## Generated Parser Policy

For the MVP release, generated Tree-sitter parser artifacts stay out of git.
The committed parser contract remains:

- `../zorg-treesitter/grammar.js`
- `../zorg-treesitter/docs/grammar.md`
- `../zorg-treesitter/queries/*.scm`
- `../zorg-treesitter/test/**`
- `../zorg/fixtures/manifest.json`

`../zorg-treesitter/README.md` documents the source policy for
`src/parser.c`, `src/grammar.json`, `src/node-types.json`, and
`src/tree_sitter/*`: they are generated by `npm run generate` and ignored by
git.

Rust source builds currently consume generated parser files from the sibling
`../zorg-treesitter/src` directory. A release operator must run
`npm run generate` before building Rust binaries. Packaged binary archives do
not need the generated C source because they include compiled `zorg` and
`zorg-ls` executables.

Neovim users obtain a compiled parser through their Tree-sitter parser manager
or a local build from `zorg-treesitter`. The Neovim plugin ships query files and
registers the `zorg` parser name, but it does not ship a compiled parser.

Do not commit generated parser artifacts or change Rust parser consumption in a
release dry run. Any future change to commit generated sources, enable npm
bindings, or vendor parser C into the Rust workspace requires a separate
release-policy change before the release tag.

## Dry-Run Command

Run the full non-publishing release dry run from the Rust repo root:

```sh
tools/release_dry_run.sh
```

The command:

1. checks required tools and sibling repository paths;
2. requires clean worktrees in all three repositories;
3. verifies Rust and Tree-sitter versions match;
4. runs the fixture manifest check;
5. runs `tools/validate_cross_repo.sh` as the pre-release gate;
6. verifies generated Tree-sitter parser outputs exist after generation;
7. builds Rust release binaries;
8. assembles a temporary local archive for the host target;
9. writes and verifies a SHA-256 checksum for that temporary archive;
10. runs non-publishing source/package inspection commands; and
11. checks that all three worktrees are still clean.

The dry-run script must not tag, push, upload, publish to crates.io or npm, or
mutate versions. Future publishing support must be added behind an explicit
flag whose name includes `publish` or `release`; the default command remains
non-publishing.

## Manual Dry-Run Checklist

Use this checklist when running the helper or doing the same work by hand.

1. Confirm repository layout:
   - Rust repo is the current directory.
   - `../zorg-treesitter` exists, or `ZORG_TREESITTER_DIR` points to it.
   - `../zorg-nvim` exists, or `ZORG_NVIM_DIR` points to it.
2. Confirm clean worktrees:
   - `git status --short --branch` in the Rust repo.
   - `git status --short --branch` in `zorg-treesitter`.
   - `git status --short --branch` in `zorg-nvim`.
3. Confirm versions:
   - Rust workspace version in `Cargo.toml`.
   - `cargo run -p zorg-cli -- --version`.
   - `cargo run -p zorg-ls -- --version`.
   - Tree-sitter version in `package.json`.
   - Neovim tag/release notes for the coordinated version.
4. Confirm changelog drafts:
   - Each repo has a `CHANGELOG.md` entry or a release-note draft with the
     required sections.
   - Cross-repo changes cite sibling commits or tags.
5. Regenerate and validate parser artifacts:
   - `(cd ../zorg-treesitter && npm install && npm run generate && npm test)`.
   - Confirm `src/parser.c`, `src/grammar.json`, and `src/node-types.json`
     exist.
   - Confirm generated files are still ignored unless a later policy says
     otherwise.
6. Run fixture sync:
   - `python3 tools/check_fixture_manifest.py`.
7. Run the pre-release gate:
   - `tools/validate_cross_repo.sh`.
8. Build Rust release binaries:
   - `cargo build --workspace --release`.
   - Confirm `target/release/zorg` and `target/release/zorg-ls` run
     `--version`.
9. Inspect temporary host artifact:
   - Create an archive named `zorg-v{version}-{target}.tar.gz` or `.zip`.
   - Confirm it includes `zorg`, `zorg-ls`, README, license files, and release
     notes.
   - Generate `{archive}.sha256`.
   - Verify the checksum.
10. Inspect source/package outputs without publishing:
    - Rust: package or archive inspection only; do not run `cargo publish`.
    - Tree-sitter: `npm pack --dry-run` only; do not run `npm publish`.
    - Neovim: inspect a `git archive` output only; do not push tags.
11. Confirm final clean worktrees in all three repos.
12. Record the dry-run result in the release notes with the date, host target,
    commit IDs, and validation command output summary.

## Rollback Notes

A failed dry run should leave no tags, pushes, uploads, or version commits. To
recover:

1. Stop at the first failing command and keep its label or output.
2. Remove temporary artifact directories printed by the dry-run script if they
   were preserved for inspection.
3. If `npm run generate` changed ignored files under `../zorg-treesitter/src`,
   delete the generated `src` directory and regenerate after fixing the source
   issue.
4. If tracked files changed, inspect them with `git status --short` and
   `git diff`. Keep intentional source fixes for a normal commit; discard only
   accidental generated or local files.
5. Rerun `tools/release_dry_run.sh` from a clean state.
